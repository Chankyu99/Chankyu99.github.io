# 1. RAG 파이프라인 코드 리팩토링

내가 주로 담당했던 RAG 파이프라인 코드를 리뷰하며, 리팩토링을 겸사겸사 진행했다.

우선 브랜치를 따로 생성하고, 새로운 코드 리팩토링을 진행했다. Codex와 함께 짠 코드를 한 줄씩 한 줄씩 적어가며 작동 원리와 그렇게 코드를 짠 이유를 말할 수 있도록 숙지하려 노력했다.

그래서 bot_logic.py 코드를 먼저 진행했다.

프로젝트의 파이프라인 실행 흐름은 다음과 같다.

1) 사용자 질문 입력 → 슬롯 추출 및 DB 항목 매핑
2) 필수 슬롯 누락 여부 체크 → 누락 시 사용자에게 재질문
3) ChromaDB에서 문서 검색
4) 검색된 문서 + 슬롯 정보를 기반으로 최종 답변 생성
5) Streamlit에 스트리밍 출력

순서대로 코드를 이해한 내용을 정리해본다.

## 국가별 카탈로그 생성

> 슬롯 추출 전, "LLM이 어떤 DB 항목 중에서 고를 수 있는지" JSONL로 저장된 문서를 읽어 국가별 물품 카탈로그를 생성한다.

```python
COUNTRIES = {"KR", "US"}

def load_country_item_catalog():
    items_by_country: dict[str, set[str]] = {country: set() for country in COUNTRIES}

    with open(DATA_FILE, "r", encoding="utf-8") as f:
        for line_num, line in enumerate(f, start=1):
            stripped_line = line.strip()

            if not stripped_line:
                continue

            record = json.loads(stripped_line)
            country = record.get("country")
            item = record.get("item")

            if country not in COUNTRIES:
                continue

            if not isinstance(item, str) or not item.strip():
                continue

            items_by_country[country].add(item.strip())

    return {
        country: sorted(items)
        for country, items in items_by_country.items()
    }
```

- 규정 문서에 있는 공식 물품 카테고리명과 사용자 입력의 물품명을 연결시키기 위한 사전 작업

# 2. 검색 품질 개선을 위한 데이터 증강 코드 리팩토링

> ChromaDB에 들어가는 문서는 어떻게 만들었고, 검색이 잘 되도록 어떤 처리를 했는가?

- 데이터 증강 의도는 사용자의 입력이 어떤 형태여도 검색을 통해 매핑을 잘되게 하려 했음

- 보통 사용자가 LLM 사용 시 "전담", "고츄장" 등 줄임말과 오타를 일으키는 경우가 빈번함
- 이런 케이스의 경우 실제로 초기 설계 시 DB 내 "농산물/식품", "액체 겔류" 라는 규정 물품명과 매핑이 안되어서 답변 생성이 아예 불가능했다.
- 규정 문서 내 카테고리명이 너무 딱딱한 용어여서 그 용어대로 입력하지 않으면 검색이 안되었기 때문이었다
- 그래서 그 용어와 관련된 키워드를 LLM으로 구축해 수동으로 입력해놓았다
- 결과적으로 ChromaDB에는 원문 규정뿐 아니라, 사용자가 실제로 입력할 만한 표현도 함께 임베딩된다

```python
def augment_record(record: dict) -> dict:
```

# 3. 증강된 데이터를 ChromaDB에 적재하기

> JSONL 로드 → LangChain Document 변환 → metadata 정리 → embedding 생성 → ChromaDB 저장

- ChromaDB에 저장할 metadata 형식으로 생성 -> 국가별 규정 문서를 따로 찾아야 하니까
- 84개의 각 레코드를 1개씩 LangChain Document 객체로 변환하고, 암배당 모델을 통해 저장

```python
def build_document(record: dict) -> Document:
    return Document(
        page_content=record.get("page_content", ""),        # 실제 검색 대상이 되는 텍스트
        metadata=build_metadata(record),                    # 국가, 문서 ID, 규정 항목명 같은 필터링 정보
    )

def build_metadata(record: dict) -> dict:
    metadata_raw = record.get("recommended_metadata", {})

    metadata = {
        key: str(value)
        for key, value in metadata_raw.items()
    }

    metadata["doc_id"] = str(record.get("doc_id", ""))
    metadata["country"] = str(record.get("country", ""))

    return metadata
```

# 4. 모델 평가

## 중간 성능 점검

> 실제로 슬롯 추출과 검색이 잘 되는지 평가했다. 질문 이해 → 슬롯 추출 → DB 항목 매핑 → 문서 검색 순으로 대체로 잘 작동하는걸 확인

- 우리가 설계한 슬롯 추출, 증강, 검색 과정이 중간에 잘 이루어져 있는지 확인
- 평가 데이터셋 역시 LLM을 활용해 수동으로 구축하고, 검색 결과와 레이턴시도 동시에 평가해보았다
- 중간 성능은 대체로 좋았다

## 최종 성능 평가

> 최종 답변 품질은 RAGAS를 이용해 실험적으로 평가했다.

- RAGAS는 RAG 애플리케이션을 체계적으로 평가하기 위한 라이브러리
- 공식 문서에서는 RAGAS를 LLM 애플리케이션을 “감”이 아니라 평가 루프로 점검할 수 있게 도와주는 도구라고 설명
- 그중 Faithfulness는 생성된 답변이 검색된 context와 사실적으로 일치하는지 측정하는 지표
- 점수는 0~1 범위이며 높을수록 좋다.

- 이번에는 여러 지표 중 Faithfulness만 우선 사용했다. 이유는 이 프로젝트에서 가장 중요한 것이 “그럴듯한 답변”보다 “검색 근거에 충실한 답변”이었기 때문
- 다만 RAGAS 평가는 내부적으로 LLM을 추가 호출한다. 무료 Gemini API를 사용하는 상황에서는 quota 제한이 있어서 30개를 한 번에 평가하지 않고, 하루에 5개씩 나누어 측정하기로 했다.

> Streamlit을 활용해 간단하게 채팅 UI를 구성, UI에서 중요한 것은 두 가지였다.

1. 사용자가 현재 어떤 슬롯 정보를 입력했는지 볼 수 있어야 한다.
2. LLM 답변이 생성되는 동안 기다리는 느낌이 덜해야 한다.

- 그래서 Streamlit의 session_state를 활용해 대화 기록과 슬롯 상태를 저장했다.

```python
def initialize_session_state() -> None:
    if "messages" not in st.session_state:
        st.session_state.messages = []

    if "slots" not in st.session_state:
        st.session_state.slots = {}
```

- messages에는 사용자와 봇의 대화 기록이 들어가고, slots에는 현재까지 추출된 출발지, 도착지, 물품 정보가 들어간다.
- 사이드바에는 현재 슬롯 상태를 보여주도록 했다.
- 이렇게 해두면 사용자가 “고추장”만 먼저 말하고, 이후 “한국에서 미국”이라고 답했을 때 현재 어떤 정보가 채워졌는지 확인할 수 있다.
- 답변 출력은 스트리밍 방식으로 처리했다.

```python
def stream_bot_response(placeholder, response_stream) -> str:
    full_response = ""

    for chunk in response_stream:
        full_response += chunk
        content_html = full_response.replace("\n", "<br>")

        placeholder.markdown(
            f"""
            <div class="chat-bot">
            <div class="sender-label">기내뭐돼 봇</div>
            {content_html}
            </div>
            """,
            unsafe_allow_html=True,
        )

    return full_response
```

- bot_logic.py의 run_pipeline()이 응답 스트림을 반환하고, app.py는 그 스트림을 받아 화면에 조금씩 출력한다.
- 덕분에 사용자는 답변이 모두 생성될 때까지 빈 화면을 보는 것이 아니라, 작성되는 과정을 실시간으로 볼 수 있다.
- 사용자 입력이 들어왔을 때의 전체 흐름은 다음과 같다.

```python
response_stream, updated_slots = run_pipeline(
    user_message=user_input,
    chat_history=st.session_state.messages[:-1],
    slots=st.session_state.slots,
)

st.session_state.slots = updated_slots
full_response = stream_bot_response(placeholder, response_stream)
```

- 결국 app.py는 RAG 로직을 직접 처리하지 않는다. 핵심 로직은 bot_logic.py에 맡기고, UI는 입력, 출력, 세션 상태 관리에 집중하도록 분리했다.
- 이번 리팩토링을 통해 프로젝트를 다음처럼 다시 정리할 수 있었다.

data_augmenter.py → 검색 품질을 높이기 위한 문서 증강
ingest.py         → 증강 문서를 ChromaDB에 저장
bot_logic.py      → RAG 파이프라인 실행
eval_rag.py       → 슬롯/검색/응답 품질 평가
app.py            → Streamlit UI 제공

- 단순히 “챗봇이 돌아간다”에서 끝나는 것이 아니라, 데이터 준비부터 검색, 답변 생성, 평가, UI까지 각 모듈이 어떤 역할을 하는지 분리해서 이해할 수 있었다.
- 특히 RAG 프로젝트에서는 LLM 프롬프트만 중요한 것이 아니라, 데이터 증강과 검색 평가가 답변 품질에 직접적으로 영향을 준다는 점을 다시 확인했다.
